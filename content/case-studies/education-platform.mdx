## Overview

This is not a single learning management system. It is a set of twelve applications that together run a digital learning business: learning, exams, a digital library, live classes, communication, payments, a store and administration, for many institutions and many kinds of users.

It combines:

- **Learning:** course management, study resources and a digital library (e-library)
- **Assessment:** online examinations, mock exams and question banks
- **Teaching:** live classes, lecturers and institute management
- **People:** student management, a guardian portal and sponsor management
- **Commerce:** payments, a vendor portal and a marketplace
- **Community:** a blog platform, social features, real-time chat and notifications
- **Operations:** platform administration
- **Clients:** web portals, Flutter mobile apps and an Electron desktop app

It is live in Sri Lanka and runs on one shared backend.

## Product evolution

### Phase 1: exam preparation for doctors

The platform began with a narrow, well-defined problem. Doctors who complete their medical education outside Sri Lanka must pass professional examinations before they can practise there. They needed somewhere to prepare.

The first product gave them that: digital study materials, online learning, mock examinations and knowledge resources, all in one place.

### Phase 2: a multi-tenant learning ecosystem

That product worked, and the platform grew from it. Instead of serving one audience, it became a multi-tenant ecosystem that many educational institutions run on, with dedicated applications for every group involved in learning: students and doctors, institutions and lecturers, guardians, sponsors, vendors, authors and the platform team.

The capabilities that made the first product work, such as study resources, mock exams and question banks, became part of a much larger platform that also handles live teaching, communication, payments, commerce and administration.

## Platform architecture

The platform is made up of twelve applications:

- **Learners:** the student web app, the Flutter student app and the desktop app.
- **Portals:** the institute, admin, guardian, sponsor and vendor portals.
- **Content and communication:** the blog platform, plus chat on web and on Flutter.
- **Backend:** the gateway that serves them all.

They are separate applications, but they are not separate systems. Four things hold them together:

- **Gateway API:** one API for every client, which also owns the database schema.
- **Shared MySQL database:** one source of truth for users, courses, enrollments and payments.
- **Shared Laravel package:** installed in every Laravel portal, it holds single sign-on, memberships, commission rules, enrollment orders, payouts and statements.
- **Single sign-on:** signed tokens let one person move between portals without signing in again.

### Why this architecture

| Decision                                 | Why                                                                                                                                     |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| A dedicated application for each group   | Institutions, guardians, sponsors, vendors and administrators do very different work. Each gets an interface built for it.              |
| One gateway API that owns the schema     | Every application works on the same data, so the schema changes in one place and every client sees the same rules.                      |
| One shared database                      | Users, courses, enrollments and payments have one source of truth instead of copies that drift apart.                                   |
| A shared package for cross-cutting rules | Sign-on, commissions, enrollments and payouts must behave identically in every portal, so they live in one package rather than in each. |
| Single sign-on between portals           | One person can be a student, a guardian and a sponsor, and should move between those roles without signing in again.                    |
| Managed services for video and real-time | Zoom and Ably carry live classes and chat, so the team's time goes into learning, exams and payments.                                   |

## Mobile and desktop

**Flutter mobile apps** are part of the same ecosystem, not separate products. Students study on them and use chat, through the same gateway API and the same rules as the web.

**The desktop app** exists to protect premium content and examinations, which a browser can't do reliably. Built with Electron for Windows, macOS and Linux, it can:

- run full screen in a locked-down kiosk mode
- block screenshots and screen capture, copy and paste, and right-click
- add a watermark identifying the user
- detect virtual machines and watch for other running processes and extra displays
- notice when the exam window loses focus
- require camera or screen-recording permission, depending on the protection level of the course or exam
- log violations for review

## Engineering challenges

**Twelve applications, one backend.** Every client reads and writes the same users, courses, enrollments and payments. Keeping the schema in the gateway, and shared rules in one package, stopped each application from growing its own version of the truth.

**Shared authentication and multi-role users.** One person can be a student, a guardian and a sponsor. Single sign-on and membership resolution let them move between portals and see only what each role allows, without separate accounts.

**Shared business rules.** Commissions, enrollment orders and payouts are used by several portals. Putting them in a shared package meant a rule changed once and behaved the same everywhere.

**Financial transactions and payment integration.** Card payments through PayHere, saved cards, bank transfers, and Apple and Google in-app purchases all have to end in the same enrollment, commission and payout records. Each path had its own callbacks and failure cases, and the result had to be correct every time.

**Real-time communication.** Chat runs on web and Flutter through Ably, so messages and groups had to stay in step across platforms.

**Desktop security across platforms.** Protection has to hold on Windows, macOS and Linux, and each operating system handles permissions differently. On macOS, for example, packaged builds behaved differently from development because the system caches screen-recording permission for the life of the process, which took careful investigation to solve.

**Scalability and maintainability.** New user groups and features kept arriving as the product evolved. Clear separation between applications, with shared rules in one place, let the platform grow without each addition making the rest harder to change.

## AI-assisted engineering

The team used Claude Code, ChatGPT and GitHub Copilot in day-to-day engineering: architecture discussions, code generation, refactoring, debugging, documentation and testing.

AI made us faster. It did not build the platform. Engineers stayed responsible for architecture, implementation, code review, testing and production decisions, and AI-assisted changes went through the same review as any other.

## Business impact

I don't publish internal figures for client work, so the outcomes below are described rather than measured.

- **From a niche product to a platform:** what started as exam preparation for overseas-qualified doctors became a multi-tenant learning ecosystem for many institutions.
- **One platform for every group:** students, doctors, institutions, lecturers, guardians, sponsors, vendors and authors work on shared data instead of separate systems.
- **More than learning:** the same platform handles exams, communication, payments, commerce and administration.
- **Less operational complexity:** institutions run their courses, students, exams and finances through one integrated platform.
- **Built to keep growing:** the shared gateway, database and package mean new applications and features fit into the existing foundation.
